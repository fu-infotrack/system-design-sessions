Locking · Lesson 1 · ~7 minutes

Efficiency or correctness?

One question, asked before you pick a lock, that decides everything downstream.

The knowledge

When you reach for a lock, you are protecting an invariant — a property that must stay true no matter how many things run at once. Before choosing how to protect it, answer one question:

The question

What does it cost if this runs twice?

There are only two answers, and they lead to different tools.

EfficiencyCorrectness
A double-run costsmoney, CPU, duplicated workwrong data
Is a sloppy lock OK?yesno
Is a lock even enough?yesnever, on its own

That second row is the useful one. If you are in the efficiency column, the cheapest thing that mostly works is the right answer — reach for it, write a comment saying the lock is approximate, and move on.

The third row is the one that surprises people. Martin Kleppmann's argument, which the Redis documentation now repeats in its own voice, is that a lock with a timeout cannot deliver correctness by itself:

You should implement fencing tokens… This applies to any distributed locking system. — redis.io, Distributed locks

Why: every distributed lock needs a time limit, because if the holder dies nothing else can release it. And the moment it has a time limit, it can expire while you are still working — a garbage-collection pause is enough. Two processes then hold it, and neither knows.

So in the correctness column, mutual exclusion is not the answer. Something must reject the stale writer — the database checking a version, or the storage service refusing a write without the current lease. We cover that in lesson 3.

The practice

Sort each of these. They are all real shapes from systems like ours. The reasoning matters more than the score — read the feedback even when you are right.

What to take away

The sort is not academic. It tells you when to stop.

  • Efficiency → a Redis lease is fine. Accept the occasional double-run and say so in a comment.
  • Correctness → do not go looking for a better lock. Go looking for a way to make the second run harmless, or to make the resource refuse it.

The most common expensive mistake on a team is spending a week hardening a lock for a problem in the right-hand column, where no amount of hardening helps.
