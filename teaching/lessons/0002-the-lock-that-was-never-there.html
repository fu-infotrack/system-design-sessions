The lock that was never there

Two ways to write a Postgres advisory lock in EF Core that look right, compile, run, log nothing — and protect nothing.

The knowledge

Postgres gives you a lock on any number you like, no row required. Perfect for "only one import per tenant at a time." There are two flavours, and the difference is the whole lesson:

FunctionScopeReleased by
pg_advisory_lock(k)the sessionan explicit unlock, or the connection closing
pg_advisory_xact_lock(k)the transactioncommit or rollback. Always

A session is a database connection. And here is the thing that catches everyone:

The trap

Under EF Core, you do not own the connection — the pool does. Your DbContext is scoped to a request. The connection underneath it is not.

Failure one: the lock outlives the request

EF Core closes the connection immediately after the statement. It goes back to the pool still holding your lock, and the next request that draws it is told it acquired the lock too. Measured:

request 1: took pg_advisory_lock(101)
request 1: DbContext disposed
   server still holds it: 1
request 2: opened, no command yet -> server holds: 1
request 2: pg_try_advisory_lock(101) -> TRUE     <-- both hold it

No exception. No log line. Session-scoped locks are stackable, so re-acquiring on a connection that already holds it simply succeeds.

Failure two: the lock that never existed

So you switch to pg_advisory_xact_lock. But if there is no explicit transaction, EF runs your statement in autocommit — a transaction that begins and ends with that one statement. The lock is taken and released in the same breath:

=== 4. pg_advisory_xact_lock with NO explicit transaction ===
  xact_lock, no explicit tx -> locks held after statement: 0

You have no lock at all, and nothing tells you. This one is worse than the leak, because the leak at least serialises something.

The rule

pg_advisory_xact_lock, inside an explicit BeginTransactionAsync(). Both halves are load-bearing.

The practice

Each of these is a plausible thing to find in a pull request. Does it protect the invariant its author intended?

What to take away

The scope of an advisory lock is the scope of the connection, not the scope of your code. Two questions settle every case:

  1. Who owns this connection — me, or a pool?
  2. Is there an explicit transaction around the lock and the work?

And note what the rule is not: session-scoped locks are not a mistake. They are exactly right when you want to hold something for the lifetime of a process — leader election, a singleton daemon — on a dedicated connection you own — a background service holding one connection for its lifetime, never borrowing from the pool that serves requests. (Libraries do this too; Marten's async daemon is one example, though we don't run it.)
