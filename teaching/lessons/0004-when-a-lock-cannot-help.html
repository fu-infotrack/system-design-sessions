When a lock cannot help

There is a class of problem where no lock, however correct, prevents the thing you are worried about. Recognising it is the single most valuable habit in this course.

The knowledge

Take the classic:

// runs on 3 pods
if (order.Status == Pending)
{
    await _payments.ChargeAsync(order);   // the side effect
    order.Status = Paid;
    await _db.SaveChangesAsync();
}

Everyone reaches for a distributed lock. Now look closely at what a lock would have to guarantee — and notice that it cannot:

The core idea

The lock and the charge cannot commit together. They live in different systems, so whatever order you choose, there is an instant where one has happened and the other has not. Crash there and you cannot tell which.

Work it through. You hold the lock, you call the payment provider, and the response times out. Did the charge happen? You cannot know. Release the lock and retry, and you may charge twice — while correctly holding the lock the whole time.

Mutual exclusion answers "is anyone else doing this?" It cannot answer "did I already do this?" — and that second question is the one that matters the moment an effect leaves your process.

The tell

Ask where the effect lands:

Lands inside your storeLeaves your store
a row update, an inserta payment, an email, a partner API
a lock can be atomic with itnothing can be atomic with it
lock, or a constraint, or a version checkidempotency

Inside your store you have a real option, because the lock and the write can commit or roll back together — that is why SELECT … FOR UPDATE in one transaction is stronger than any Redis lease. Outside, you need the operation to be safe to repeat, which is a property of the operation, not of who is allowed to run it.

The usual mechanism is an idempotency key the far side deduplicates on — you send the same key, they charge once. Most payment and messaging APIs support it. How to build that is session 3's subject (Competing Consumer & Idempotency); here we only need you to recognise when you have reached the boundary.

The practice

For each, decide whether a correctly-working lock would actually prevent the problem.

What to take away

When the effect leaves your process, a lock demotes from the solution to an optimisation. It stops duplicate work most of the time, which may be worth having — but it is not what makes you correct, and it should not be described in the code as though it is.

The sentence to carry into review: "a lock stops two people doing it at once; it does not stop one person doing it twice."
