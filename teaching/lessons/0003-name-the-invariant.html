Name the invariant

The question to ask in code review, and why most answers to it are the wrong kind of sentence.

The knowledge

An invariant is something that must stay true about your data or the world, no matter how many things run at once.

When someone adds a lock, ask what it protects. You will get one of two kinds of answer, and they are not equally useful:

An invariantA symptom
"A card is charged once per order""Two threads shouldn't run this method"
"A room has no overlapping bookings""There's a race here"
"A customer has one active subscription""It breaks under load"

The left column describes the world. The right column describes your code. That difference decides what you can do next:

Why it matters

An invariant can be enforced somewhere other than a lock — a unique index, a version check, a routing decision. A symptom can only be defended against. If you cannot name the invariant, a lock is a guess.

The test

A good invariant survives this question: could someone violate this without running my code at all?

"A customer has one active subscription" survives — a migration or a manual `INSERT` could break it, which tells you the database should hold the rule. "Two threads shouldn't run this method" does not survive; it is not a fact about anything, and there is nowhere to put it but a lock.

The practice

For each pull request comment, is the stated reason an invariant or a symptom?

Now name one yourself

A colleague wraps this in a distributed lock:

var draft = await db.Invoices.SingleAsync(i => i.Id == id);
draft.Number = await NextNumberForTenant(draft.TenantId);
await db.SaveChangesAsync();

What is the invariant?

What to take away

Three words, in review: "protecting what, exactly?"

If the answer is a property of the data, you have options — and lesson 4 and the framework will give you several better than a lock. If the answer is a property of the code, push back before the lock goes in: the design is not understood yet, and a lock will preserve the misunderstanding rather than fix it.
