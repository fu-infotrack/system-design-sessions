Locking decision card

A lock is never the goal. Protecting an invariant is.

The seven questions, in order

1 Can the data store enforce it?
unique index · partial unique index · EXCLUDE · optimistic concurrency → no lock
2 Does the effect leave the store, and is it unsafe to repeat?
payment, email, partner API → idempotency key. A lock cannot fix this. A deterministic overwrite is safe to repeat — fall through
3 Can contention be made structurally impossible?
partition by key · actor/grain · one designated writer → no lock
4 What is the blast radius?
threads → Interlocked / lock / SemaphoreSlim(1,1) · one machine → named Mutex, Global-prefixed
5 Is the database the shared state?
row exists → FOR UPDATE · queue → SKIP LOCKED · no row → pg_advisory_xact_lock in an explicit transaction
6 Efficiency or correctness?
efficiency → Redis SET NX PX + compare-and-delete unlock; accept double-runs
7 Can the resource reject a stale writer?
yes → fencing token or lease-enforced write · no → stop and restructure. Return to 1, 2 or 3

Before you write it

Must answer

  1. What invariant am I protecting?
  2. What does a double-run cost?
  3. Effect outside the store, unsafe to repeat?
  4. What is the blast radius?

Then pick

  1. How long is the critical section?
  2. How much contention?
  3. Can the resource fence?
  4. How will I know it broke?

Leases you already have

Any system that hands you work with a timeout and reassigns it if you do not confirm is a lease, and can expire mid-work.

SystemThe leaseDefault
Service Bus peek-lockLockDuration1 min, max 5
Kafka partitionmax.poll.interval.ms5 min
Redis lockkey TTL30 s
Azure blob leaseDuration30 s (15–60 s or ∞)

Never answer an overrun with a bigger number. Longer lease = slower recovery from a dead worker; shorter = more zombies. Make the second run harmless instead.
