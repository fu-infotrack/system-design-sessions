And on Windows

Same trap.
Different mechanism.

Unprefixed means Local\ — per Terminal Services session. A service runs in session 0, a desktop app in session 1+.

A WSL process and a Windows process never share a named mutex. "Works on my machine" tells you nothing here.

The rule

pg_advisory_xact_lock
inside an explicit transaction

A session lock is bound to the connection. Under EF Core you don't own the connection — the pool does.

Both halves matter. Without the transaction, autocommit releases it in the same breath: no lock at all.

So how do you decide?

Before you write any lock

Four questions

  1. What invariant am I protecting?
  2. What does a double-run cost?
  3. Where does the side effect land?
  4. What's the blast radius?

Question 2 is the fork

EfficiencyCorrectness
A double-run costsmoneywrong data
Sloppy lock OK?yesno
Is a lock enough?yesnever, alone

Where does your current work sit?

The tree

1. Can the data store enforce it?          -> no lock
2. Side effect outside the store?          -> idempotency
3. Contention structurally avoidable?      -> no lock
──────────────────────────────────────────────────
4. Blast radius?                           [demo 1]
5. Is the DB the shared state?             [demo 2]
6. Efficiency or correctness?              [demo 3]
7. Can the resource reject a stale writer? -> fence
                                           -> or restructure

Most people start
at step 4.

The job of the framework is to make steps 1, 2 and 3 happen first.

Step 7, when the answer is no

Stop. Restructure.

A framework that always produces an answer is lying. Some designs cannot be made correct with a lock.

Go back to 1, 2 or 3 — the three exits.

Remember three things

  1. Name the invariant. If you can't, you don't need a lock — you need to think harder.
  2. Distributed locks expire while you hold them. Design for it, or don't use one.
  3. If the side effect leaves your process, you need idempotency, not mutual exclusion.
